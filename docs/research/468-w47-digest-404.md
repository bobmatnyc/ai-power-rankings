# #468 follow-up: 2026-W47 weekly digest 404 on 2026-11-23

Read-only research. Probes: 2 curl requests to aipowerranking.com, `gh run view` reads.

## Conclusion

The page 404 is correct: no `weekly_digests` row for 2026-W47 exists. The page, the revalidation and the week key are not at fault. The cron most likely ran and skipped with `no-articles` (HTTP 200, no alert), because daily ingestion has produced 0 articles for the last 3 runs. A cron that never fired or that failed are the other candidates; only a Vercel log read separates them.

## Q1. Trace and week key

- Cron `30 7 * * 1` (`vercel.json:8-9`) calls `GET /api/cron/weekly-digest` (`app/api/cron/weekly-digest/route.ts:84`), which calls `generateWeeklyDigest` (route.ts:105).
- `lib/services/weekly-digest.service.ts:237`: `previousIsoWeek(new Date())`, which is Monday 00:00 UTC of the current ISO week minus 7 days (`lib/weekly-digest-window.ts:~60`).
- Week arithmetic: 2026-01-01 is a Thursday, so W01 starts 2025-12-29. 2026-11-23 is 329 days later (47 weeks), so it starts W48. At 07:30Z on 2026-11-23 the cron computes W47 (Nov 16 to 22). It cannot generate W48 and there is no off-by-one: the UTC Monday boundary is exact at 07:30Z.
- `digestWeekKey` (`scripts/lib/live-site-checks.mjs:61-66`) matches: before 09:00Z it returns two weeks back (W46), from 09:00Z one week back (W47). Its 09:00Z cutoff was a guess about when the row lands, not a computed schedule. Today's 08:15Z and 09:33Z checks of W47 are therefore valid expectations only after 09:00Z.
- Flow with outcomes:
  - service.ts:242: row already stored: skip `already-stored`.
  - service.ts:246-248: `digestTier(articles.length)` is null: skip `no-articles`, HTTP 200, no alert, no row.
  - service.ts:268-: LLM draft, then `repository.save`, then `revalidateDigestPages(week)` (service.ts:309).
  - Failure: 500 and `sendCronAlert`, which is a no-op when `ALERT_WEBHOOK_URL` is unset (route.ts:31).
- Page 404 conditions (`app/[lang]/whats-new/weekly/[week]/page.tsx:29-34`): `windowForWeek(week)` null (bad key; W47 is valid) or `getStoredDigest(week)` returns no row. A DB read failure throws and gives a 5xx, not a 404.

## Q2. Static generation / cached 404

- `page.tsx:13` `revalidate = 1800`; `page.tsx:15-17` `generateStaticParams` returns `[]`. `dynamicParams` is not set, so it defaults to true and unknown weeks render on first request, then are cached as ISR.
- A cached `notFound()` is an ISR entry and `revalidatePath` clears it. `digestPagePaths` (service.ts:75-83) revalidates the exact path `/${lang}/whats-new/weekly/${week}` for every locale, so it matches the page route.
- Revalidation runs only after a successful write (service.ts:309), so a skip or failure never purges the cache.
- Probe: `curl .../en/whats-new/weekly/2026-W47` returned `404`, `x-vercel-cache: HIT`, `age: 120`, `cache-control: public, max-age=0, must-revalidate`. The `Date` header read 08:15:49 GMT while the real time was about 09:35Z, so the 404 is a cached copy. The ISR window is 30 minutes, after which the next request revalidates against the DB. A cached 404 will not persist beyond that unless the row is still absent. Treat the cached 404 as a consequence of the missing row, not a cause. Unproven: the odd `Date`/`age` pair suggests the entry was not regenerated since 08:15; a second probe after 30 minutes would show whether it refreshes.

## Q3. Non-Vercel evidence

- Gap-detector run 45144960897 (2026-11-23T09:13Z), job "Check last weekly digest" passed and logged `LAST_DIGEST_WEEK=2026-W46`, `LAST_DIGEST_GENERATED=2026-11-17T12:30:30Z`. Newest stored row is W46 as of 09:13Z, so no W47 row existed then.
- The W46 row was generated Tuesday 12:30Z, not at Monday 07:30Z: it came from a manual or forced run after the #468 fix (PR #469 merged 2026-11-17 ~07:56 -0500, #472 after). So the cron has not yet produced a row on its own since the fix. The Monday 2026-11-16 run was the 500 from #468.
- The gap detector passes for W47 until generated_at is older than 8 days (`scripts/check-weekly-digest-gap.mjs`, `MAX_DIGEST_AGE_HOURS = 8*24`). It would alert about 2026-11-25 09:00Z (W46 generated 11-17 12:30Z plus 8d is 11-25 12:30Z, so the 11-26 run in practice). It cannot flag W47 earlier.
- Same run, job "Check last ingestion run": `ALERT[ZERO_YIELD_STREAK]: last 3 runs all ingested 0 articles (most recent: 2026-11-23T06:00:00Z)`. This points to Q4 cause 1.
- RSS `/en/whats-new/rss.xml` (lastBuildDate 09:35:45Z) lists W46 and W45 as the newest weekly links, no W47.
- No public endpoint exposes cron invocation logs.

## Q4. Ranked causes

1. No-articles skip (most likely). The W47 window (Nov 16 to 22) had too few active articles because ingestion yielded 0 for 3 runs (ZERO_YIELD_STREAK above). `service.ts:246-248` returns skip with HTTP 200 and no alert. Log would show `Cron: weekly digest run complete` with `status: "skipped", reason: "no-articles", week: "2026-W47"`. Check the `articles` table for `published_date` in the window to confirm (needs a DB read, not done).
2. Cron did not fire or answered 401. `CRON_SECRET` mismatch gives 401 (route.ts:87-98) and an alert only if `ALERT_WEBHOOK_URL` is set. Log would show a 401 or no invocation at 07:30Z. History in `cron-gap-detector.yml` header notes CRON_SECRET misconfig has silenced crons before.
3. Generation failure: LLM empty or rejected output (`WeeklyDigestEmptyError`, `WeeklyDigestError`, service.ts:67-129), or a 300s `maxDuration` timeout (route.ts:52). Log would show a 500 with `Cron: Failed to generate weekly digest`. Fix #469 addressed one empty-output path only.
4. Written but not purged, or DB-write false negative: ruled out. The detector read W46 as newest at 09:13Z and the RSS (force-dynamic) has no W47.
5. Week key off-by-one or ISO/UTC boundary: ruled out (Q1).

## What a Vercel log read confirms

For `/api/cron/weekly-digest` at 2026-11-23 07:30Z: status code (200 vs 401 vs 500), and for a 200 the JSON body or the `Cron: weekly digest run complete` line with `status`/`reason`. A 200 with `no-articles` confirms cause 1; no invocation or 401 confirms cause 2; 500 confirms cause 3.

## Follow-ups (not done, no authority)
