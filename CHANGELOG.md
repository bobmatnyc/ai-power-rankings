## [Unreleased]

### Removed
- chore: the abandoned Payload CMS integration. `components/payload/` (`AdminDashboard.tsx`, `SubscribersManager.tsx`, `ToolsManager.tsx` and the `admin-dashboard-stats.ts` helper added in #142) had no importer anywhere in the tree — the live admin UI is `components/admin/`, whose own `AdminDashboard`, `ToolsManager` and `unified-admin-dashboard` are what the `app/[lang]/(authenticated)/` routes render — so `tests/unit/admin-dashboard-stats.test.ts` went with it, being that helper's only consumer. Two scripts that could no longer run were deleted alongside: `scripts/debug-rankings.ts` imported `payload` and `@payload-config`, neither of which exists (`payload` has never been a dependency in `package.json`, and no tsconfig path alias defines `@payload-config`), and `scripts/analyze-news-ingestion.ts` imported `lib/payload-direct`, a module absent from the repository. Both sit under the `scripts/**/*` tsconfig exclusion, which is why dangling imports survived every `tsc` run. `PAYLOAD_SECRET` is gone from `lib/env.ts`, where nothing read it, and the Payload claims in `app/api/rankings/README.md` and `app/api/tools/README.md` — which described the live routes as "Uses Payload CMS" when both read Drizzle repositories — now name the repositories those routes actually call. `hooks/use-payload.ts` and `lib/richtext-utils.ts` are kept despite their names: the first is imported by `components/admin/tools-manager.tsx` and fetches this project's own JSON API routes rather than a CMS, and the second is imported by four live files to parse stored RichText content

### Fixed
- fix(build): `npm run build` runs `generate-categories` before `next build`, and with no `DATABASE_URL` that script rewrote the committed `lib/data/static-categories.ts` down to a single "All Categories" entry with a fresh `Generated:` timestamp and exited 0 — a developer who built locally and committed wiped 57 lines of category data behind a diff that looked routine. Two swallowed failures caused it: `fetchCategoriesFromDb()` caught every connection and query error and returned the placeholder as if it were a real read, and a snapshot with no rankings row produced that same placeholder. Both now propagate. `scripts/generate-static-categories.ts` keeps only environment, database and filesystem access; the write/skip/fail decision moves to `lib/data/static-categories-generator.ts` as a pure async function over injected dependencies (`hasDatabaseUrl`, `allowEmpty`, `fetchCategories`, `writeFile`, `log`, `logError`) returning the exit code, so every branch is reachable from `tests/unit/generate-static-categories.test.ts` with no database. The matrix: no connection string configured prints one line saying regeneration is skipped and the committed file is kept, touches nothing and exits 0, so local builds keep working; a connection or query error prints the message with any `postgres://` / `postgresql://` URL redacted (this repository is public and the build log is not private), touches nothing and exits 1; a read of zero categories prints that the file was left untouched and exits 1 unless `--allow-empty` is passed, which writes the empty result and exits 0; a read of one or more categories writes as before. The write itself is now atomic — a temp file beside the target, then a rename — so a crash mid-write cannot leave the module truncated. The guard asks `hasUsableDatabaseUrl()` in `lib/db/connection.ts` rather than reading `process.env` a second time, so it cannot disagree with what `getDb()` will do. Vercel is unaffected: `DATABASE_URL` is set there, so the build regenerates the file exactly as it did (#143)
- fix(build): review follow-up on the above. The generate-categories guard first mirrored `getDatabaseUrl()` by ORing `DATABASE_URL`, `DATABASE_URL_DEVELOPMENT` and `DATABASE_URL_STAGING`, but that function is conditioned on `NODE_ENV` and in production — which is what a Vercel build runs as — reads `DATABASE_URL` only. An environment carrying just `DATABASE_URL_STAGING` therefore passed the guard, reached `getDb()`, and threw, turning a skip into a failed build. The branching rules move to `lib/db/database-url.ts` as `resolveDatabaseUrl(env, nodeEnv)` — a pure function reading no globals — which `getDatabaseUrl()` now calls (its four log lines are reconstructed by `describeDatabaseUrlResolution` from the same result, so `getDb()`'s output is unchanged) and which the new exported `hasUsableDatabaseUrl()` wraps for the script. The script's own variable list is deleted. Because the resolver takes its environment as an argument, `tests/unit/generate-static-categories.test.ts` drives every `NODE_ENV` without mutating `process.env` and without importing the connection module, whose import runs dotenv — so the tests depend on no `.env*` file existing (#143)
- fix(admin): every card on `components/payload/AdminDashboard.tsx` showed 0. The component read `totalDocs` from `/api/news`, `/api/tools` and `/api/rankings`, and `docs[0].period` for the ranking period — the Payload CMS collection shape, which none of these routes has ever returned, so all four values fell through `|| 0` and rendered a zero indistinguishable from a real count. `/api/admin/subscribers` made it worse: no route implements that path, so it answered 404 with an HTML body, `.json()` threw, and because all four fetches shared one `try` the throw skipped the single `setStats` call — every card stayed at its initial zero even for the three endpoints that had answered fine. Each response is now read independently through a helper that returns `null` on a non-2xx status or an unparseable body, and each count comes from the field its route actually emits: `total` for news, the length of the returned `tools` array (the route takes no parameters and returns every active tool), and `stats.total_tools` plus top-level `period` for rankings. A count that could not be read renders an em dash rather than 0, so "no rows" and "could not reach the endpoint" stay distinguishable. "Last Generated" displayed `new Date()` — today's date, whatever had actually happened — and now reads the snapshot's `published_at` as "Rankings Published", falling back to "N/A" on the no-rankings-yet branch, which omits that field. The response-to-count mapping moves into `components/payload/admin-dashboard-stats.ts` as a pure function over one interface per endpoint; the interfaces declare no `totalDocs`, so a repeat of this typo is a `tsc` error rather than a silent zero (#140 follow-up)
- fix(api): `/api/news?limit=100&offset=300` returned `news: []` and a `total` of 300. The route fetched a fixed `getPaginated(limit * 3, 0)` pool, classified each row's `event_type` in JavaScript, then filtered and `.slice(offset, offset + limit)`d that pool — so no offset past the pool could resolve and `total` was the pool length, not the count. `event_type` was the only reason the pool existed and it is not a stored column, so the keyword ladders it was derived from move into SQL (`lib/db/news-event-type.ts`, one `CASE` cascade over `tags` then `title || summary-or-content`, same rung order); the SELECT list, the `WHERE` and the `COUNT(*)` now read that one expression, and nothing is filtered after the fetch. `NewsRepository` gains `getPaginatedFiltered()` and `countFiltered()` — real `LIMIT`/`OFFSET`, a real `COUNT(*)`, and `id` breaking `published_date` ties so a row cannot repeat on one page and vanish from the next — with `getPaginated()` left for its other callers. `limit` is clamped to 100 and `offset` floored at 0, and a non-numeric value falls back to the default instead of reaching the statement as NaN. `/api/news/recent` had the same shape: it fetched the top 100 by published date and applied `days` in memory, silently truncating any window holding more than 100 articles — the lower bound, the ordering and the bound are now one query over `COALESCE(published_date, created_at)`. Response shapes, cache headers and the per-item `event_type` the news page filters on client-side are unchanged (#140)
- fix(ci): migration `0013_add_candidate_outcome_tracking.sql` shipped with the #133 deploy and was never applied, so production ingestion was down from 2026-09-04 — migrations are applied by hand and nobody can pull a production `DATABASE_URL` to a laptop. A dispatchable **Apply database migration** workflow (`.github/workflows/apply-migration.yml`) runs the apply from CI against the existing `DATABASE_URL` repository secret, the same one `cron-gap-detector.yml` already queries production with: dispatch once with `dry_run: true` to see the on-disk files, the ones recorded in `_drizzle_migrations` and the target table's columns without writing anything, then again with `dry_run: false` to apply exactly the named file. `scripts/apply-migrations.ts` gains the `--dry-run`, `--only <file>`, `--force` and `--show-columns <table>` flags behind it; `--only` refuses non-zero on a filename that is missing or already recorded rather than re-running its statements, `--force` (valid only alongside `--only`) lifts that second refusal for the one named file and keeps its existing tracking row rather than inserting a second — the escape hatch for a migration the old splitter recorded without executing, `--dry-run` does not even create the tracking table, and every message is stripped of anything URL-shaped so a driver error cannot carry the connection string into this public repository's Actions log. The statement splitter is also fixed: it dropped any chunk whose first characters were `--`, which meant applying 0013 executed neither of its `ALTER TABLE`s while still recording the file as applied — both sit under a leading comment line. Workflow inputs are shape-checked in shell and reach it only through `env:` mapping (#134)
- fix(ingestion): the 2026-09-05 and 2026-09-06 cron runs returned HTTP 200 but wrote no row to `automated_ingestion_runs`, logging `column "articles_skipped_stale" of relation "automated_ingestion_runs" does not exist`. #133 added `articles_skipped_stale` and `candidate_outcomes` to the Drizzle schema and shipped migration 0013, which is applied by hand and had not been run before the deploy. `updateRun()` already retried without the two columns, but `createRun()` ran first and had no such path. Leaving the columns out of `.values()` did not keep them out of the statement — Drizzle's insert builder names every column of the table and passes `default` for the omitted ones, and a bare `.returning()` lists them all a second time, so both halves referenced columns the database lacked. `createRun()` now seeds the row through an explicit column list and returns only `id`, writing the same values it wrote before; a remaining undefined-column error retries once on `run_type`/`status`/`started_at` and lets the database defaults fill the rest, and any other error still propagates (#134)
- fix(ci): review follow-up on the gap-detector fallback trigger — three ways it could fire or leak when it should not. `createRun()` takes no lock and run 483bd3e8 sat at `status='running'` permanently, so `check-ingestion-gap.mjs` now ends every outcome with `LAST_STATUS=` and `LAST_RUN_STARTED=` lines and the workflow refuses to call production while the latest row is still `running` (a second pipeline would run concurrently against the same tables); the gap check still goes red. `STALLED` is evaluated independently of the other three conditions, so it can co-occur with `RUN_FAILED`/`OPENROUTER_CREDITS`/`ZERO_YIELD_STREAK` — which mean the cron *is* firing; those now suppress the trigger and the issue names which one did. When the fallback call returns 2xx and the re-check still fails, the reason line distinguishes "wrote a row and that run then failed" (a non-STALLED alert in the re-check) from "wrote nothing" (still STALLED at the same `LAST_RUN_STARTED`), instead of asserting the latter in both cases. Auto-close now matches the issue title as well as the `ingestion-alert` label, so a human-labeled unrelated issue is left open. The response body no longer reaches the issue raw: this repository is public and the route's 500 path returns `error.message` verbatim, so only a JSON `error` string survives, with token-shaped runs and anything after `key`/`token`/`secret`/`bearer` replaced by `[redacted]` before a 200-character cap — a non-JSON body (an HTML error page, a proxy banner) is dropped entirely (#134)
- fix(ci): the ingestion gap detector could only report that no run row had landed; it could not tell a Vercel scheduler that never fired from one that fired and got a silent 401, which is the distinction the 2026-09-04 stall (#134) turned on. On `ALERT[STALLED]` only — never on `RUN_FAILED`/`OPENROUTER_CREDITS`/`ZERO_YIELD_STREAK`/`NO_RUNS_EVER`, where the cron is demonstrably firing — the workflow now calls `GET $PRODUCTION_BASE_URL/api/cron/daily-news` from the runner with the `CRON_SECRET` repository secret, then re-runs `scripts/check-ingestion-gap.mjs` (the same query, not a second copy of the SQL) and records the verdict in the alert issue: a 401 means GitHub's secret and Vercel Production's have diverged, a 2xx plus a fresh row is a recovery, a 2xx with no new row means the route returned success and wrote nothing. With no `CRON_SECRET` configured the call is skipped and the issue says so. A `force_trigger` dispatch input runs the same call on demand, replacing `scripts/trigger-ingestion.ts` as the backfill path. The workflow also closes every open `ingestion-alert` issue once the check passes, and the STALLED remediation text now walks the Vercel Cron Jobs tab and function logs instead of asserting a redeploy as the recurring root cause — repo history records no case of a redeploy fixing a stall. `app/api/cron/daily-news` gains its first tests, pinning that an unauthorized request never constructs `AutomatedIngestionService` and that an unset `CRON_SECRET` cannot be satisfied by an empty bearer (#134)
- fix(ingestion): the 2026-09-03 06:00 UTC run ingested three articles the same day with `published_date` of Aug 20, Aug 21 and Aug 30, so `/api/news/recent?days=1` returned nothing and the gap detector saw a healthy run. Every freshness mechanism keyed off Tavily's self-reported date, and nothing recorded that the `time_range=day` recency pass (#125) had found a result. Search results now carry `discoveredVia` (recency/window) and dedupe by that tag rather than by array position; the freshness gate never drops a recency-pass candidate for a stale provider date, and the freshest-first sort orders on a provisional date (the provider date when it is inside the window, else the run's discovery time for a recency candidate). At insert, a deterministic resolver replaces `metadata.publishedDate || analysis.published_date` — the LLM-extracted article date wins when it parses, is not future-dated, and is inside the window; then the provider date; then, for a recency candidate only, the run's discovery time; else the previous fallback — and records which rule won as `publishedDateSource` on the article's processing log. The run row gains `articles_skipped_stale` (opportunistic fix: the count was computed every run but `updateRun` never mapped it and no column existed, so it was silently dropped) and `candidate_outcomes`, a capped per-candidate list of URL, pass, dates, outcome and reason, so "a fresh candidate existed and failed to insert" is distinguishable from "no fresh candidate existed". Both write only through `updateRun`, and a write that predates migration 0013 retries without them so the terminal status and existing counters still land (#132)
- fix(ingestion): a 429-triggered auto-block (extended in #127) never expired — it shared the same permanent-for-process-life semantics as a 401/403/"blocked" refusal, so one rate-limited run could starve an otherwise-healthy source for the rest of a warm serverless process. A 429-only trigger now records a 4-hour TTL (`AUTO_BLOCK_TTL_MS`); `isDomainBlocked()` treats an expired entry as unblocked and evicts it lazily on read. 401/403/"blocked" triggers are unchanged (#126)
- fix(ingestion): a pipeline that hit `PIPELINE_TIMEOUT_MS` and was marked `status='failed'` could still have its own abandoned, still-running `executeDailyDiscovery` call overwrite that row later with a stale `completed`/`partial` and a reset `completedAt` — `runDailyDiscovery`'s `Promise.race` never cancels the losing side. `updateRun()` now guards any write carrying a terminal `status` with `WHERE status = 'running'` in the same UPDATE, so a write that loses the race matches zero rows and is silently skipped instead of downgrading an already-terminal row; counter-only checkpoint writes stay unguarded and continue to apply (#128)
- fix(news): the "Referenced Links" section on article pages could carry the source site's own footer/sister-site navigation instead of story references (e.g. an Insurance Journal article listing mynewmarkets.com, claimsjournal.com, insurancejournal.tv, ijacademy.com, carriermanagement.com) — none share the source article's domain, so a same-domain filter alone could not catch them. The ingestion prompt now instructs the model to include only links that are directly story-relevant and actually appear in the source, allowing an empty block; a new deterministic `sanitizeRelatedLinksBlock()` independently verifies each link the model returns against the actual source content/hrefs it was shown and drops anything unverifiable or shaped like nav/footer chrome, applied at ingestion time for new articles. A render-time `filterChromeLinks()` heuristic (anchor-text/domain matching, no access to the original source) also runs on every article's display, including already-stored ones, as a best-effort backstop (#122)
- fix(ingestion): a run row could stay stuck `status='running'` with all counters at 0 even after articles were successfully ingested under it (seen on run 483bd3e8, 2026-08-29) — every finalization write funneled through a single `updateRun()` call per exit branch, each with its own log-and-swallow catch and no retry, so one failed write (e.g. a dropped DB connection near a serverless timeout) abandoned the row forever with the gap-detector unable to see it. Persistence is now centralized into one retrying, never-throwing `finalizeRun()` helper called from a single `finally` block covering every exit path, plus a checkpoint write of the accrued counters immediately after the ingest loop so a failure later in the pipeline can no longer leave the row at all-zero (#124)
- fix(ingestion): discovery could go days without surfacing same-day content — Tavily ranks by relevance, not recency, so a same-day story could rank below several-days-old ones and miss the result cutoff entirely, and the two `maxArticles` caps downstream then truncated in that relevance order rather than by freshness. Discovery now issues an explicit `time_range: 'day'` recency pass alongside the existing days-bounded pass (additive, not narrowing), and all candidates are sorted freshest-source-date-first before either cap so a same-day item can no longer be crowded out by an older, higher-relevance one (#125)
- fix(ingestion): extraction failures from a source that rate-limits (HTTP 429, e.g. `devin.ai`) are now treated the same as 401/403/"blocked" and auto-block the domain for the rest of the run. Root cause went deeper than the missing 429 case: `TavilyExtractService.extractContent()` swallowed its own error and returned `null` after exhausting retries, so the auto-block check downstream never received the provider's error text for ANY status code — it now throws once retries are exhausted (matching `JinaReaderService`'s existing behavior), and the auto-block check moved to the extraction-chain catch blocks that actually observe it (#125)
- fix(news): article detail pages rendered the same links twice — an in-body "Related Links" block and a "Referenced Links" section beneath it, with identical content. Both came from one field: the ingestion prompt appends a `**Related Links:**` markdown block to `rewritten_content`, which rendered as prose, while the detail component separately regex-extracted every markdown link out of that same string. The in-body block is now stripped before the prose is rendered, so "Referenced Links" is the page's only links section; extraction still reads the original content, so the surviving list stays populated for already-stored articles. Repeated URLs are also deduplicated by URL
- fix(ingestion): freshness gate — an auto-discovered article whose SOURCE published date is older than `FRESHNESS_WINDOW_DAYS` (default 14) is now skipped before any extraction or LLM spend, and never counts toward `articlesIngested`. Since ~2026-08-20 every discovered article carried a date weeks to months old, so runs inserted rows and reported healthy positive yield while nothing surfaced in any publishedDate-ordered or -filtered view (recent news, sitemap top, the monthly editorial's month window). A run that discovers articles but yields zero fresh ones now records `articles_ingested = 0` against a positive `articles_discovered`, so the existing `ZERO_YIELD_STREAK` alert in `scripts/check-ingestion-gap.mjs` fires
- fix(ingestion): the daily cron called `runDailyDiscovery()` with no arguments, so the Tavily `days` lookback was `undefined` and omitted from the request — discovery was relevance-ranked with no date bound at all. It now defaults to the freshness window; an explicit `--days` still wins and widens the gate in step

### Changed
- feat(ci): `scripts/check-ingestion-gap.mjs` could say a run ingested articles but not whether any of them reached the feed, which is exactly what the 2026-09-07 06:00 UTC run needed answering. Every outcome now also prints a detail block for the latest run: `INGESTED_ARTICLE_IDS=<count>` plus one `INGESTED_ARTICLE` line per recorded id joined to its `articles` row (`slug`, `status`, `published_date`, `created_at` — `slug=null` means no row matched the id at all, since `articles.slug` is NOT NULL), then `CANDIDATE_OUTCOMES=<total>`, one `CANDIDATE_OUTCOME` line per distinct outcome with its count, and one `CANDIDATE_INGESTED` line per `ingested` candidate carrying its URL and every date field the outcome recorded (`sourceDate`, `provisionalDate`, `effectiveDate`, `publishedDateSource`). The block is strictly appended and strictly additive: `withRunDetail()` copies `ok`/`exitCode` rather than recomputing them, so diagnosis cannot turn the gap check red or green, and `OK:`/`ALERT[...]`/`LAST_STATUS=`/`LAST_RUN_STARTED=` keep their exact text and position for the greps in `cron-gap-detector.yml`, which is otherwise unchanged. A run row predating migration 0013 — or a database without those columns, which the `to_jsonb(r) -> 'col'` projection reduces to NULL instead of an error — prints `unavailable` rather than failing, and a detail query that throws prints one `DETAIL_ERROR=` line. Anything URL-shaped is stripped from error text (this repository is public and the output is pasted into an issue body), candidate URLs are truncated to 120 characters and cannot inject a newline or a forged `ALERT[...]` into the log the workflow greps, and each list is capped at 50 lines with the overflow reported as a count (#138)

Reshapes the SWE-bench contribution for all 31 tools (surfaced in the impact analysis); factor weights unchanged
